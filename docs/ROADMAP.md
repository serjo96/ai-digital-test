## 1. Цель и границы

Получить из 220 строк поставщиков канонические товары с одной категорией, нормализованными предложениями, прослеживаемыми характеристиками, короткими проверенными описаниями и очередью неопределённых случаев. Показать качество на небольшой проверенной человеком выборке и объяснить, какая работа выполняется кодом, а какая моделями.

Сначала создаём работающую кодовую основу и измеримый baseline. После этого выбираем AI-подходы по конкретным ошибкам. Кодовый baseline — промежуточный результат, а не замена требуемой AI-части: в финале должны быть реальные модельные вызовы и обоснование их ролей.

Не входят в MVP: auth, deployment, multi-tenant, курсы валют, внешний каталог товаров, vector database, распределённые очереди, универсальный парсер любых supplier feeds, полноценная админка. Один локальный процесс/приложение, файловые входы и сохранённые результаты достаточны. Стек выбрать и записать в начале этапа 1 по знакомости и скорости реализации; отдельное исследование стеков не нужно. Для этапа 3 пользователь выбрал OpenAI Sol и Astra; рабочий адаптер OpenAI отделён общим контрактом от pipeline. Ollama пока только будущая интеграция.

### Приоритеты

- **P0 — обязательно:** учёт всех строк; сохранение оригиналов; разделение товара и предложения; защита от ложных объединений; evidence; удержание конфликтных и неподтверждённых утверждений; eval; реальные AI-вызовы; обязательные документы; минимальный экран.
- **P1 — улучшить после рабочего P0:** полнота объединений, качество пограничной классификации, уменьшение необязательного review, удобство просмотра ошибок.
- **P2 — только по измеренной необходимости:** embeddings, дополнительные модели, многоступенчатые исправления текста, расширенная UI-редактура.

Ограничение PDF — примерно 5–6 часов сосредоточенной работы. Ориентир для реализации: этап 1 — 70 минут, 2 — 65, 3 — 65, 4 — 65, 5 — 65; всего 330 минут и до 30 минут резерва. Это ориентир, не обещание: учитывать фактическое время, включая разметку. Если не укладываемся, сокращать P2/P1 и честно описывать незавершённое, не скрывать отсутствие проверки или AI. Ожидание API/ответа пользователя учитывать отдельно.

## 2. Решения MVP, с которыми начинаем

| Тема | Решение |
|---|---|
| Источник | Обрабатывать JSON. Пример PDF с совпадающим row_id не дополнительный источник фактов. Оригинальные файлы не перезаписывать. |
| Товар | Каноническая сущность — модель и различимый вариант. Явные отличия Pro, поколения, ёмкости, цвета, переключателей или комплектации не стирать. Отсутствующее значение не считать автоматически ни совпадением, ни противоречием. |
| Предложение | Supplier, SKU, цена, stock, состояние и условия продавца сохраняются отдельно. OPEN BOX не новая модель. Остатки автоматически не суммировать. |
| Цены | Amount + currency, исходная строка сохранена. `$` трактовать как USD — явное допущение. Денежные значения хранить без ошибок двоичной арифметики. Без FX и единой «лучшей цены» между валютами. |
| Источники | Нет привилегированного поставщика. Большинство, минимум или среднее не доказывают истинность спорной характеристики. |
| Конфликты | Удерживать спорную характеристику, сохранять наблюдения и причину. Остальные факты могут пройти, если идентичность товара достаточно определена. Неразрешённое объединение блокирует публикацию объединённой карточки. |
| Неполнота | Unknown остаётся unknown. Пустые specs не делают товар мусором. Заголовок тоже источник; первое слово не автоматически бренд. |
| Единицы | Нормализовать совместимые величины; сохранять смысл, условия и ограничители. Допуск округления явно определить для поддержанных полей, не вводить универсальный процент на всё. |
| Категории | Только 12 значений taxonomy. Ear tips, tablet cases и laptop sleeves → other; обычные мыши без gaming-признаков → other; USB-C hubs → chargers_cables. Это рабочие правила границ, а не эталон заказчика. Не-товары получают отдельный статус, не other. |
| Описание | Короткий нейтральный английский текст, ориентир 1–3 предложения без обязательного минимума specs. Не дополнять сведения внешними знаниями. |
| Публикация | Локальный статус готовности и разрешённый текст, без внешней публикации. Черновик и разрешённая версия различаются. Ошибка проверки не разрешает публикацию. |
| Review | Достаточно очереди с причинами и evidence; ручное редактирование/approve workflow не обязательны. Confidence привязан к конкретному решению; начать с high/medium/low и причин, не выдавать его за вероятность. |
| Разметка | Около 20 содержательных случаев matching и связанные с ними примеры утверждений. AI-черновик становится эталоном только после проверки человеком. |
| API | По PDF ключ предоставляет организатор. Запросить перед этапом 3, если ещё не получен. До этого кодовые этапы не блокируются; секреты не сохранять в репозитории. |

## 3. Минимальная модель данных и распределение ответственности

Сущности нужны для прослеживаемости, не для построения универсального framework:

- **SourceRow / Offer:** исходная запись, результаты нормализации, состояние обработки и диагностические причины.
- **Fact:** атрибут, значение, единица, ограничители/условия, принадлежность товару или предложению, row_id, поле и цитата источника. Производное нормализованное значение сохраняет исходное наблюдение и правило преобразования.
- **CanonicalProduct:** ID, исходные row_ids, признаки идентичности, категория, confidence и причины решения.
- **ReconciledFact:** все наблюдения, статус согласования, разрешённое значение либо причина удержания.
- **Listing / Claim / ReviewItem:** черновик, проверенные утверждения и evidence, итоговый текст/статус, причины review.
- **RunReport:** версии входов и конфигурации, метрики, ошибки, время; позднее модель, промпт, вызовы и стоимость.

Код отвечает за схему, идентификаторы, парсинг однозначных значений, арифметику, проверку наличия цитат, явные несовместимости, применение политики публикации и расчёт метрик. Модель позже помогает с семантическим извлечением, неоднозначным сопоставлением/категориями, генерацией и смысловой проверкой. Наличие дословной цитаты не доказывает entailment: модель и оценка должны учитывать, о каком предмете и условиях говорится.

## 4. Этапы — один этап на отдельный чат

| Этап | Результат | Зависимость | Статус |
|---|---|---|---|
| 1. Кодовая основа и измеримый baseline | Запускаемый проект: загрузка → нормализация → простое сопоставление → отчёт; eval-контур | Исходные файлы | Кодовая часть завершена; разметка provisional |
| 2. Надёжные решения по товарам и фактам | Согласование, категории, evidence, review и улучшенный кодовый baseline | Этап 1 | Кодовая часть завершена; B1-v2, provisional eval |
| 3. AI для выявленных семантических ошибок | Реальный структурированный extraction/matching и сравнение с baseline | Этап 2, API | Кодовая интеграция проверена офлайн; live B2 отложен пользователем |
| 4. Генерация и проверка публикации | Полный pipeline с измеренным verifier и разрешённым текстом | Этап 3 | Не начат |
| 5. Экран, итоговая оценка и передача | Проверяемый локальный MVP, финальный benchmark и документы | Этап 4 | Частично выполнен на B1; итоговая оценка ожидает этапы 3–4 |

### Этап 1. Кодовая основа и измеримый baseline

**Задача:** получить первый работающий проход по всем данным и возможность измерять изменения. Создание структуры проекта входит сюда, но не является самостоятельным результатом.

**Объём:**

1. Выбрать простой знакомый стек, создать структуру, lockfile, команды запуска/проверок, `.gitignore` и безопасный пример конфигурации без ключей. Начать README и журнал AI_USAGE фактическими действиями.
2. Загрузить оба JSON, валидировать схему и идентификаторы, сохранить оригиналы. Нормализовать пробелы/регистр для сравнения, известные форматы цены; выделить очевидный мусор по содержимому, не по row_id или одному stock=0.
3. Реализовать baseline B0: группировка по консервативно нормализованному заголовку; неоднозначные строки остаются отдельными/в review. Это диагностический ориентир с известными пропусками, не заявка на правильный matching.
4. Подготовить примерно 20 оценочных случаев с row_ids, ожидаемыми группами, похожими отрицательными примерами и коротким объяснением. Случаи разделить по товарным семействам: ориентир 14 development и 6 holdout; связанные варианты не распределять между ними. Подготовить данные для человеческой проверки. Непроверенные метки явно обозначить provisional.
5. Сделать eval, сохраняющий JSON-результат и читаемый отчёт: аудит входа, matching, список ошибок, время. Зафиксировать первый baseline; пока нет проверенных меток — качество provisional/N/A, не выдуманные нули.

**Выход:** запуск на 220 строках без API; нормализованные записи, группы B0, черновик/подтверждённая разметка, первый отчёт и команды в README.

**Критерий завершения:** 220/220 строк учтены без потери и двойного назначения; повторный кодовый запуск даёт те же решения/метрики; eval обнаруживает известное ошибочное объединение и пропущенную пару на маленьком контрольном примере; цены и опасные случаи имеют содержательные проверки. Генерация и verifier пока N/A. Непроверенная человеком разметка остаётся явным открытым пунктом, не блокирует независимую кодовую работу.

### Этап 2. Надёжные решения по товарам и фактам

**Задача:** построить предметные правила и наблюдаемую обработку неопределённости до AI.

**Объём:**

1. Ввести сущности товара, предложения и фактов; извлекать кодом только поддержанные однозначные форматы. Не писать универсальный многоязычный parser. Сохранять непонятый текст для следующего этапа.
2. Добавить простой поиск кандидатов по названию/модели и проверки явных несовместимостей. Сходство — повод рассмотреть пару, не разрешение объединить. Проверять совместимость групп, чтобы A≈B и B≈C не склеивали несовместимые A и C.
3. Нормализовать поддержанные единицы, определить правила округления на примерах Nimbus/LedgerLite; отличать пропуск от конфликта и несопоставимых условий. Сохранять признак «до», вид скорости, «с кейсом» и scope предложения.
4. Классифицировать очевидные типы правилами в закрытую taxonomy, остальные помечать для review с допустимой категорией other. Добавить согласование фактов, confidence с причинами и список review.
5. Сохранить B1 и сравнение с B0 на development. Добавить проверки Nimbus/Pro, AeroBuds/ear tips, OPEN BOX, пустых specs и одинаковых шаблонных specs разных моделей.

**Выход:** кодовый pipeline выдаёт товары, предложения, факты, категории, конфликты и review. Видно, какие ошибки требуют семантического разбора.

**Критерий завершения:** ключевые случаи воспроизводятся отдельными проверками; отсутствие данных не превращается в выдуманные факты; несовместимости не теряются при объединении; сохранены метрики B0→B1 и объяснение ухудшений, если они есть. Нерешённая семантика допустима и явно перечислена.

### Этап 3. AI для выявленных семантических ошибок

**Задача:** проверить, какую измеримую пользу дают модели поверх кодовой основы.

**Объём:**

1. На ошибках B1 определить нужные роли: структурированное извлечение признаков/фактов, неоднозначные пары и категории. Кратко сравнить подходящие доступные модели по качеству, формату ответа и задержке. Проверить актуальную официальную документацию при выборе; не выбирать только по цене. Ограничить исследование 1–2 кандидатами и общей небольшой development-выборкой.
2. Подключить реальный API. Строгий выход: значения + row_id + поле + цитата, unknown при недостатке данных. Проверять схему и существование источников кодом; необоснованный результат не принимать.
3. Добавить timeout, ограниченные retries и обработку невалидного ответа как review/error. Кэшировать по входу, версии схемы, модели, параметрам и промпту. Изменение входа/промпта не должно незаметно использовать старый ответ.
4. Пропускать извлечённые сведения через уже существующие правила группировки, конфликтов и публикации. Не позволять модели обходить явные ограничения и назначать авторитетность поставщика.
5. Сравнить B2 с B1; измерить ошибки извлечения, candidate recall и matching. Заполнить реальные роли в LLM_ROLES, включая немодельные шаги, ошибки, стоимость/задержку.

**Выход:** воспроизводимый запуск с реальной моделью, кэш, сравнительный отчёт и обоснованное распределение ролей.

**Критерий завершения:** есть реальный успешный модельный прогон, evidence проходит структурные проверки, сбои не принимаются как успех; сохранены B1→B2 и решения по наблюдаемым ошибкам. Если усложнение не помогает, сохраняем более простой вариант и документируем эксперимент. Отсутствующий ключ блокирует именно реальный AI-результат; mocks не заменяют выполнение задания.

### Этап 4. Генерация и проверка публикации

**Задача:** получить короткий текст и проверить каждое его утверждение, включая контекст и конфликты.

**Объём:**

1. Генерировать из разрешённых фактов, не из бесконтрольного объединения raw text. Для недостаточных данных допустим минимальный текст по заголовку либо удержание с причиной.
2. Отдельным шагом проверять весь сгенерированный текст по исходным строкам и решениям о конфликтах, а не только по пересказу генератора. Атомарные claims должны покрывать весь текст; встроенное неподтверждённое прилагательное тоже утверждение. Отдельный вызов может использовать ту же модель, но не является гарантированно независимой проверкой.
3. Код применяет результат: supported можно допустить; disputed/unsupported удерживаются; unknown/error блокирует соответствующий текст. После изменения текста перепроверить целиком. Максимум одна попытка исправления; затем review, без бесконечного цикла.
4. Подготовить и проверить человеком набор поддержанных утверждений и контролируемых искажений на тех же товарных случаях: другое число, чужая характеристика, снятый ограничитель, неверный scope, конфликт. Не выдавать эти искусственные ошибки за естественную частоту галлюцинаций.
5. Измерить verifier и результат полного pipeline B3. Помимо фиксированных искажений проверить небольшую выборку реально сгенерированного текста; результаты двух оценок показывать отдельно.

**Выход:** черновик, claims с evidence и вердиктами, разрешённый текст или причина удержания, полный benchmark B3.

**Критерий завершения:** проверка выполнялась на настоящем тексте; поддержанные примеры тоже включены; нет известных пропущенных опасных утверждений в принятой проверенной выборке; если есть — исправление или явное удержание, не сокрытие метрик. Все карточки получают текст/черновик либо объяснимый статус. Review и полезный выход измерены: блокировка всего не считается успехом.

### Этап 5. Экран, итоговая оценка и передача

**Задача:** сделать результат обозримым и воспроизводимым из чистого клона.

**Объём:**

1. Один экран: выбор/список товаров и фильтр review; карточка с категорией/confidence, предложениями, raw rows, фактами/конфликтами, черновиком и разрешённым текстом. Утверждение ведёт к своему источнику и причине допуска. Экран читает тот же сохранённый результат pipeline, не содержит отдельную демонстрационную логику.
2. Запустить финальный вариант на 220 строках и один раз оценить holdout после фиксации правил/промптов. Отдельно показать development и holdout, абсолютные ошибки, matching, verifier, покрытие и время/стоимость.
3. Завершить README, LLM_ROLES.md, одностраничный WRITEUP.md, AI_USAGE.md. Записать 2–3 компромисса, реальные сбои, сокращения и продолжение на неделю. Истории об ошибках AI брать из журнала, не придумывать.
4. Проверить установку из чистого клона/чистого окружения, запуск pipeline, eval и UI. Различить replay сохранённых ответов и live API. Без ключа можно показывать сохранённый результат, но нельзя заявлять новый AI-прогон.

**Выход:** локальный MVP и комплект сдачи. Фактическая отправка репозитория/ZIP организаторам — отдельное действие пользователя.

### Основные показатели

| Показатель | Определение и знаменатель | Когда появляется |
|---|---|---|
| Учёт строк | Число уникальных входных row_ids с одним исходом / 220; отдельно потерянные и двойные назначения | Этап 1 |
| Matching precision | TP / (TP + FP), где пары предсказаны из принадлежности одной итоговой группе | Этап 1 |
| Matching recall | TP / (TP + FN), эталонные положительные пары — строки одного размеченного товара | Этап 1 |
| Candidate recall | Найденные положительные эталонные пары / все положительные пары; до решения об объединении | Этап 2 |
| Unsupported detection recall | Заблокированные неподтверждённые claims / все размеченные неподтверждённые claims | Этап 4 |
| False block rate | Заблокированные подтверждённые claims / все размеченные подтверждённые claims | Этап 4 |
| Disputed leakage | Допущенные спорные claims / все размеченные спорные claims | Этап 4 |
| Published claim errors | Неподтверждённые или спорные claims среди проверенных человеком разрешённых claims / все проверенные разрешённые claims | Этап 4 |
| Доля готовых карточек | Ready / все сформированные канонические карточки; рядом абсолютное число и число строк за ними | Этап 4 |

| Производительность | Wall time полного прогона; отдельно ошибки/вызовы API, токены и оценка стоимости, попадания в кэш | Этап 1, расширяется в 3 |

Если знаменатель равен нулю, результат N/A, не 0% и не 100%. Рядом с процентом всегда показывать дробь и абсолютные TP/FP/FN. Matching считать только по полностью размеченным связям; неизвестные отношения не превращать в отрицательные. Проверять ложные объединения между разными размеченными случаями, а не только внутри каждого. Присоединение неразмеченной строки отмечать как unevaluated, не засчитывать как успех. По возможности включать в случай все строки выбранного семейства из входа.

Категории, обработку мусора и извлечение ключевых фактов проверять на тех же размеченных случаях: верно/проверено плюс список ошибок. Валидность taxonomy отдельно от смысловой правильности категории. Для маленькой выборки не строить сложную сводную «оценку качества», скрывающую разные ошибки.

### Правила принятия изменений

1. Сначала зафиксировать B0 и версию проверенной разметки. Затем каждое существенное изменение сравнивать с B0 и последним принятым вариантом на development. До человеческой проверки подписывать оценки provisional.
2. Цели безопасности на проверенных случаях: 0 потерянных/двойных строк; 0 категорий вне taxonomy; 0 отсутствующих источников у принятых фактов; 0 известных ложных склеек ключевых разных моделей/аксессуаров; 0 известных неподтверждённых/спорных утверждений в разрешённом тексте. Это критерии данной выборки, не обещание универсального качества.
3. Не принимать улучшение recall ценой нового критического ложного объединения или пропущенного опасного утверждения. Не принимать рост безопасности, достигнутый скрытым падением полезного выхода до нуля.
4. После B0 зафиксировать фактические ориентиры recall/покрытия/review. Универсальный порог 95% до измерений не назначать. Если trade-off нужен, записать до/после, конкретные случаи и причину выбора.
5. Менять один существенный фактор за эксперимент. Сохранить гипотезу, конфигурацию, результат и решение: принять / отклонить / отложить. Не запускать много комбинаций ради рейтинга моделей.
6. Кэшированный replay использовать для сравнения правил; fresh API — для оценки live-поведения и времени. Эти режимы не смешивать. Повторный live-прогон нужен при подозрении на нестабильность, а не автоматически для каждой правки.

### Что сохранять на запуск

Run ID; дата; версия кода и отметка незакоммиченных изменений; хэши feed/taxonomy/labels; split; версия правил/схемы; модель/параметры/промпт при наличии; режим live/replay; метрики и абсолютные числа; решения по строкам/группам/claims; список ошибок; время и использование API. Исходный baseline не перезаписывать. Ключи и секретные заголовки не логировать. Предусмотреть читаемый diff отчётов и exit code для нарушенных обязательных условий.

## 6. Реестр рисков и экспериментов

| Проблема / сигнал | Первый подход | Когда усложнять | Как проверить |
|---|---|---|---|
| Разные языки/написания пропущены | Нормализация + признаки модели | Candidate recall показывает пропуски: extraction, затем при необходимости embeddings | Candidate recall и итоговый matching, не просто похожесть |
| Nimbus/Pro, аксессуары склеены | Явные различия типа/варианта, проверка группы | Семантически неоднозначная пара остаётся нерешённой: точечный LLM | Новые FP, hard-negative случаи |
| A–B–C образуют неверную группу | Проверка совместимости при присоединении к группе | Только если правила не покрывают наблюдаемые случаи | Отдельный пример с несовместимыми A и C |
| Цитата есть, смысл неверный | Сохранять предмет, scope и ограничители | Семантическая проверка извлечения/утверждения | Неверный объект, «до», «с кейсом», read speed |
| Конфликт чисел/округление | Нормализация единиц, сопоставимость условий, удержание | Новые реальные случаи требуют другого правила | Nimbus, LedgerLite, AeroBuds; не усреднять конфликт |
| Пустые specs/маркетинг | Unknown, короткий текст или review | Дополнительная модель только при доказанной пользе на доступном тексте | Выдуманные факты и полезный выход |
| Все блокируется | Корректные позитивные claims в eval | Пересмотреть причины отказа, а не убрать проверку | False block rate, ready/review, сохранённые факты |
| Модель отвечает не по схеме/падает | Валидация, ограниченные retries, review | Более надёжная модель/формат после измерений | Число сбоев, время, успешные реальные ответы |
| Растёт время и сложность | Один проход, файловые результаты, минимум вызовов | Только если доказан выигрыш на фиксированной выборке | Качество, время, стоимость и размер изменения |

Первый эксперимент AI — структурированное извлечение с evidence поверх B1. Второй возможный — точечное решение сложных пар/категорий. Embeddings — условный третий вариант, не обязательство roadmap. Генерация и verifier входят в обязательный объём независимо от этих экспериментов.
