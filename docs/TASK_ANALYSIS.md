# Shelf Ready: анализ задачи до планирования

Дата: 2026-09-08. Источники: две страницы `AI-Digital-Take-Home-Shelf-Ready.pdf`, все 220 записей `supplier_feed.json`, весь `taxonomy.json`.

Это анализ требований, данных и неопределённостей. Архитектура, стек, модели, план реализации и итоговая разметка пока не выбраны. Ниже явно разделены условия задания, наблюдения и предлагаемые допущения.

## 1. Какую проблему требуется решить

Из неоднородных предложений поставщиков нужно получить канонические товары с описаниями, которые можно публиковать на основании предоставленных источников. Нужно сохранить связь с исходными строками, выявить противоречия и передать человеку случаи, в которых решение ненадёжно.

Ключевая сложность — цепочка зависимостей: ошибка объединения товаров подмешивает чужие характеристики; затем генератор и проверяющий могут согласованно принять неверное описание, поскольку оно действительно подтверждается ошибочно присоединённой строкой. Поэтому проверка текста сама по себе не доказывает правильность всей системы.

Самый важный отдельный результат по PDF — `LLM_ROLES.md`: обоснование распределения работы между моделями и обычным кодом. Один большой промпт на всё и неоправданный отказ от моделей прямо названы неправильными подходами.

## 2. Что прямо требуется

| Область | Требование | Что должно быть наблюдаемо в результате |
|---|---|---|
| Сопоставление | Объединить строки одного реального товара | Канонический товар и прикреплённые исходные строки; похожие разные товары не склеены |
| Нормализация | Привести бренды, единицы и цены к согласованному виду | Нормализованные значения с сохранением исходных данных |
| Классификация | Одна категория на канонический товар | Значение только из закрытого списка 12 категорий |
| Согласование | Решить, что публиковать при расхождениях характеристик | Выбранное или удержанное значение и запись о расхождении |
| Генерация | Короткое описание для покупателя | Описание каждого канонического товара, с учётом ограничений публикации |
| Проверка | Проверить каждое утверждение по исходным строкам | Неподтверждённые утверждения не попадают в публикуемую версию |
| Неопределённость | Confidence и очередь проверки человеком | Понятные причины направления на проверку |
| Оценка | Вручную разметить около 20 items | Метрики сопоставления и обнаружения неподтверждённых утверждений; абзац о сбоях |
| Интерфейс | Достаточно одного экрана | Канонический товар, исходники, сгенерированный текст, флаги |

Фраза «withheld or flagged, never published» требует аккуратной интерпретации: одного значка рядом с неподтверждённым утверждением в опубликованном тексте недостаточно. Разделение черновика и разрешённого текста — предлагаемое понимание этого ограничения, а не заданная в PDF схема данных.

Обязательные материалы: Git-репозиторий ссылкой или ZIP; запуск из чистого клона; README с установкой, запуском и eval; `LLM_ROLES.md`; одностраничный `WRITEUP.md` с архитектурой, 2–3 компромиссами, продолжением на неделю и сокращённым объёмом; `AI_USAGE.md` с инструментами, делегированием, 2–3 промптами и конкретной ошибкой AI, которую удалось обнаружить.

В `LLM_ROLES.md` нужны шаг, работа модели, модель/уровень, почему модель вместо кода, последствия ошибки, примерные стоимость и задержка. Также нужен хотя бы один сознательно немодельный шаг и объяснение.

Ограничения: примерно 5–6 часов сосредоточенной работы; pipeline и роли моделей важнее полировки UI; стек и провайдер свободные; API-ключ обещают предоставить; ограничения затрат/использования не задаются, но оценки стоимости и задержки всё равно нужны. Секреты не коммитить. Auth, deployment, multi-tenant вне объёма. Далее — 30-минутный разбор и небольшое изменение вживую.

## 3. Фактические входные данные

В папке проекта на момент анализа только три исходных файла; готового приложения и готовой разметки нет.

| Показатель | Факт |
|---|---|
| Строки | 220 |
| Поставщики | EuroStock GmbH 54; Direct2Retail 46; clearance-lots 42; PacRim Trading 41; NordicDist 37 |
| Схема | В каждой записи есть `row_id`, `supplier`, `supplier_sku`, `raw_title`, `raw_specs`, `price`, `stock` |
| Типы | Все поля строковые, кроме целочисленного `stock` |
| Идентификаторы | 220 уникальных `row_id`; повторов пары supplier + supplier_sku нет |
| Пропуски | 23 пустых raw_specs; 1 пустой raw_title; 2 пустые price; отсутствующих ключей нет |
| Остатки | От 0 до 499; четыре строки с нулевым остатком |
| Форматы цены | 37 с £; 54 с EUR; 40 с явным USD; 86 с символом $; 2 пустые; одна строка `0` |
| Совпадения заголовков | После trim + casefold: 169 уникальных заголовков; 48 повторяющихся групп, включающих 99 строк |

Последняя строка таблицы — диагностический подсчёт, не число реальных товаров и не результат matching. Совпадающие названия не гарантируют тождество, а разные названия не исключают его.

Категории: `audio_headphones`, `audio_speakers`, `wearables`, `laptops`, `tablets`, `phones`, `cameras`, `home_kitchen`, `gaming_accessories`, `storage`, `chargers_cables`, `other`. Определений и примеров границ категорий нет.

Отдельных полей brand, manufacturer model, GTIN/EAN, condition, currency, языка, времени обновления, авторитетности поставщика нет. Эти сведения либо частично содержатся в тексте, либо отсутствуют. Нельзя считать первое слово каждого названия доказанным брендом.

В PDF пример с `row_9b67e4c70b` описывает AeroBuds, но в JSON этот ID относится к Juniper tablet case. Реальная строка AeroBuds с SKU ND-4417 — `row_bdbc045131`, остаток 61, а не 184 из примера PDF. Это расхождение примера и данных: для обработки и ссылок на evidence следует использовать JSON; пример PDF не считать дополнительной записью.

| Случай | Конкретное наблюдение | Почему важно |
|---|---|---|
| Разные языки и написания | SONY WH-880N / Sony Corp. WH880N Kopfhoerer; Lumen X20 Compact Digital Camera / Kompaktkamera | Обычного точного сравнения названий недостаточно |
| Похожие разные модели | Nimbus 2: 12W, 14h, 1.2kg; Nimbus 2 Pro: 24W, 18h, 1.6kg | Нельзя стирать Pro как несущественное слово |
| Товар и аксессуар | AeroBuds Pro и replacement ear tips, `row_fe3ff4b356` | Совместимость не означает один товар; аксессуар остаётся самостоятельным продуктом |

| Маркетинг вместо фактов | Sony OPEN BOX: AMAZING SOUND, BEST HEADPHONES 2026 | Текст присутствует в источнике, но не становится доказанной характеристикой |
| Очень мало информации | Slate 11: пустые specs; Volt 65W GaN charger 3-port: только new in box в specs | Заголовок тоже источник, но нельзя додумывать экран, память, протоколы или распределение мощности |
| Нет specs у всей очевидной группы | Две строки Quill 3 desk lamp, `row_6668f30f9e` и `row_4d609c9ff9`, обе пустые | Объединение не всегда восполняет недостаток информации |
| Необычные цены | Cobalt Pro USB-C hub: $23.99 и $867.99 | Разброс — повод для проверки, но без внешнего эталона нельзя исправить цену или отвергнуть товар |
| Один поставщик, несколько SKU | EuroStock: Harbor smart scale; Kestrel 2 bookshelf speaker pair; Torrent X bookshelf speaker pair | Нельзя вводить правило «максимум одна строка поставщика на товар»; суммирование stock также требует осторожности |
| Повторяющиеся шаблоны | Многие разные action camera имеют 4K60 и waterproof to 10m | Совпавшие specs не доказывают тождество модели |

Четыре явно проблемные строки: `row_f4de4c72c5` — уведомление PRICE DROP со ссылкой на отсутствующий attached sheet; `row_7f570b374f` — TEST ROW DO NOT IMPORT; `row_80738b0804` — пустой товар; `row_28c6da70ee` — MIXED PALLET. PDF прямо относит подобные случаи к не-товарам для этой задачи. Их нужно учитывать явно, а не превращать в обычные товары категории other. Совпадение этих четырёх строк с нулевым stock не доказывает, что нулевой остаток всегда означает мусор.

## 5. Что не определено и влияет на результат

1. **Граница товара.** Не указано, когда цвет, объём памяти, переключатели, комплектация или состояние создают отдельную каноническую сущность. Предлагаемое допущение: отличающиеся модели/варианты не смешивать; состояние хранить на уровне предложения. OPEN BOX сам по себе не новая модель.
2. **Достоверность источников.** Нет приоритетов поставщиков, дат или эталонного каталога. Наличие утверждения в строке доказывает происхождение, но не фактическую истинность. Предлагаемое допущение: не назначать источник авторитетным по названию и не разрешать конфликт простым голосованием без оговорок; спорную характеристику удерживать, сохраняя подтверждённые остальные.
3. **Цена.** Не определено, нужна ли общая валюта, какой курс и на какую дату, что означает $, как учитывать налог, какую цену публиковать. Предлагаемое допущение: нормализовать amount + currency на уровне предложения; не конвертировать без необходимости. USD для $ — отдельное явное допущение, а не гарантированный факт.
4. **Единицы.** Нет канонических единиц и допуска округления. Их можно выбрать и документировать. Нельзя механически смешивать разные виды величин: например, battery with case и время самих наушников, read speed и неопределённую speed.
5. **Таксономия.** Неясны категории для ear tips, tablet case, laptop sleeve, обычной мыши и USB-C hub. Предлагаемое допущение: явно описать границы и использовать other для допустимых товаров без подходящей категории; other не заменяет статус rejected.
6. **Текст и публикация.** Нет языка, длины, тона, минимального набора характеристик, целевой площадки. Предлагаемое допущение: короткое нейтральное английское описание по доступным фактам; при недостатке evidence показывать черновик/причину удержания. Фактическая интеграция публикации не задана.
7. **Confidence и review.** Не заданы шкала, пороги, допустимая доля очереди и ручные действия. Число модели не следует выдавать за откалиброванную вероятность. Нужно знать, к какому решению относится сигнал: объединению, категории, характеристике или тексту.
8. **Оценка.** Items могут означать строки, пары или канонические группы; конкретные метрики и пороги не заданы. Проверка unsupported claims требует примеров с неподтверждёнными утверждениями: при их отсутствии нельзя доказать способность их обнаруживать.

## 6. Уточняющие вопросы по приоритету

Вопросы подготовлены для обсуждения; никому не отправлены. Большинство неопределённостей допускает продолжение с описанными допущениями, поэтому не нужно ждать ответов на весь список.

**Имеет смысл задать организаторам:**

1. Правильно ли считать канонический товар конкретной моделью/вариантом, а OPEN BOX и new in box — свойствами предложения поставщика, не отдельными товарами?
2. Достаточно ли нормализовать цены как сумму и исходную валюту? Если нужна общая валюта, какая, по какому курсу/дате, и означает ли $ именно USD?
3. При конфликте характеристик есть ли приоритет поставщиков? Если нет, допустимо ли удерживать спорную характеристику и публиковать остальные подтверждённые факты, направляя конфликт на review?
4. Под «около 20 items» подразумеваются строки, пары или группы товаров? Допустима ли отдельная небольшая выборка с вручную внесёнными неподтверждёнными утверждениями для оценки verifier?
5. Для какого провайдера будет ключ и как получить его? Это нужно до реального запуска моделей; ключа среди трёх переданных файлов нет.

**Можно решить самостоятельно и записать как допущения:** язык и длина описания; канонические единицы; правила пограничных категорий; формат confidence; работа очереди только как списка причин или с ручным подтверждением. Эти вопросы стоит поднимать отдельно лишь при наличии у организаторов конкретных ожиданий.

Не требуется спрашивать о стеке, разрешении на AI-инструменты, необходимости auth/deployment или допустимости сокращения UI: PDF уже отвечает на это.

## 7. Ограничения достоверности будущего результата

- Без эталонной разметки пока неизвестно точное число канонических товаров. 169 заголовков не являются эталоном.
- Разметка около 20 items даёт ограниченное свидетельство качества, особенно если выбрать только простые случаи. Нужны как реальные совпадения, так и похожие разные товары, неоднозначности и недостаточные данные.
- В matching важны обе ошибки: ложное объединение и пропущенное объединение. Доля верных решений по всем возможным парам может выглядеть высокой из-за множества очевидно разных товаров.
- Для verifier нужно учитывать как пропущенные неподтверждённые утверждения, так и ошибочную блокировку подтверждённых. Дополнительно важно видеть, сколько полезных описаний/утверждений прошло: блокировка всего не доказывает полезность системы.
- Поддержка утверждения исходником не устраняет конфликт между исходниками. Нужно различать supported, disputed и unsupported по смыслу, даже если будущие статусы будут называться иначе.
- Сохранение ограничителей критично: up to 1050MB/s read не равно гарантированной скорости 1050MB/s; 20h with case не равно 20h без кейса; IPX4 не обосновывает произвольные обещания водонепроницаемости.
- Указание 3yr warranty у одного предложения Vault SSD не доказывает условия гарантии всех продавцов. Аналогично нельзя распространять new in box на весь товар.
- Поле supplier_feed — данные, а не инструкции для модели. Даже TEST ROW DO NOT IMPORT следует обрабатывать как признак тестовой записи по правилам системы, а не как команду, способную управлять её поведением. Вредоносные инъекции в файле не установлены; это граница доверия при будущей обработке.
- Результат должен воспроизводиться из чистого клона. Без фиксированной разметки, сохранённых решений/параметров и понятного режима работы моделей трудно сопоставлять повторные результаты; конкретные механизмы относятся к следующему этапу.
- AI может помочь подготовить черновик разметки, но без человеческой проверки нельзя честно назвать его hand-labelled ground truth. Текущий анализ также не является ручной оценочной разметкой.

## 8. Готовность к следующему этапу

Данных достаточно для проектирования решения: схема входа, закрытая таксономия, обязательные результаты, границы времени и основные сложные случаи доступны. Для понимания задания не требуются внешний поиск товаров, дополнительный каталог или загрузка данных в стороннюю систему; вымышленные или похожие модельные названия нельзя «исправлять» по знаниям модели.

До реализации следует закрепить допущения об идентичности товара, цене, конфликтах, критерии допуска текста и единице разметки. Отсутствие ответов организаторов не блокирует анализ и проектирование при явном документировании допущений. Доступ к API нужен для реального модельного прогона, а человеческая проверка разметки — для честного заявления о выполнении hand-labeling.

Следующий этап — план решения на основе этих требований и решений. В этом документе он намеренно ещё не составлен.
