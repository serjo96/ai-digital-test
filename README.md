# Shelf Ready — этап 1

Локальный кодовый baseline: JSON → валидация → нормализация → группировка B0 → development eval и отчёты. Все исходные предложения сохраняются. Это диагностический результат, без классификации, согласования фактов, генерации и публикации.

Стек: TypeScript 5.9, NestJS 12, Node 24.14.1, npm; зависимости фиксированы в `package-lock.json`. TypeScript знаком владельцу проекта и достаточен для файловой обработки 220 строк. NestJS используется как standalone application context с сервисом pipeline, без HTTP. Структура создана вручную; Nest CLI не требуется. React выбран для этапа 5 и пока не добавлен. БД, Docker, очереди и API-ключи не нужны.

## Запуск

Из корня проекта, с Node из `.nvmrc`:

```sh
npm ci
npm run typecheck
npm test
npm run pipeline
npm run eval
```

`npm test` компилирует TypeScript и запускает `node:test`, включая CLI-тесты во временных директориях. `npm run build` доступен отдельно. `pipeline` и `eval` запускают один и тот же полный B0 + development eval; каждый создаёт новый каталог в `reports/local/`. Holdout не оценивается. Встроенной команды для оценки holdout пока нет.

Параметры путей и идентификатора:

```sh
npm run pipeline -- --feed supplier_feed.json --taxonomy taxonomy.json --labels eval/labels.json --out reports/local --run-id my-b0
npm run eval -- --out reports/local --run-id my-repeat
npm run compare -- --before reports/local/my-b0 --after reports/local/my-repeat --out reports/local --run-id my-comparison
npm run compare -- --before none --after reports/local/my-b0 --out reports/local --run-id my-initial-comparison
```

Существующий каталог запуска не перезаписывается: используйте новый `--run-id`. Вариант `--before none` означает отсутствие прежнего pipeline: предыдущие метрики и дельты N/A. CLI-параметры имеют приоритет над `FEED_PATH`, `TAXONOMY_PATH`, `LABELS_PATH`, `REPORTS_DIR`, затем используются значения по умолчанию из примера выше. `.env.example` документирует переменные; `.env` автоматически не загружается.

## Данные и правила B0

- Feed — непустой массив: строковые `row_id`, `supplier`, `supplier_sku`, `raw_title`, `raw_specs`, `price`; stock — неотрицательное безопасное целое. Идентификаторы и supplier/SKU уникальны; taxonomy содержит ровно исходные 12 категорий. Дополнительные поля исходной строки сохраняются. Некорректные входы не дают успешного частичного результата.
- Ключ заголовка: trim → схлопывание пробелов → нижний регистр. Числа, пунктуация, Pro, ёмкость, цвет, комплектация и OPEN BOX не удаляются. Перевода, семантического сопоставления и проверки конфликтов specs нет. Поэтому B0 намеренно пропускает часть совпадений; одинаковое название само по себе не доказывает идентичность.
- Не-товары: пустые title+specs, точные характерные уведомления PRICE DROP/attached sheet, TEST ROW DO NOT IMPORT, MIXED PALLET/ASSORTED ELECTRONICS. Определение по содержимому, не row_id или stock. Непустые specs без названия дают отдельный исход review.
- Предложение остаётся в `rows[].source` без изменений; stock не суммируется. Группа содержит только отсортированные rowIds, SHA-256 ID, ключ заголовка и метод группировки. Она не является готовой канонической карточкой.
- Цена: `£264.99`, `769,99 EUR`, `USD 187`, `$129` → точная десятичная строка amount и GBP/EUR/USD. Для `$` записано допущение USD. `0` без валюты → amount `0.00`, currency null, `unknown_currency`; пустые и неподдержанные форматы получают собственный статус. FX и исправлений цен нет.
- У строк сохраняются диагностические причины, включая проблемы цены. `reviewRows` сейчас считает только исход missing-title review; полноценная предметная очередь и её метрики относятся к этапу 2.

## Оценка

`eval/labels.json` содержит 20 случаев (108 строк): 14 development / 6 holdout. Все метки provisional. `eval/REVIEW.md` содержит исходники и инструкцию для проверки человеком. Разметка подготовлена AI с просмотром данных; человеческой проверки ещё не было. Семейства целиком отнесены к одному split. Holdout просматривался при подготовке меток, но не оценивается и не используется для настройки B0.

Каждый случай содержит ожидаемые группы, не-товары и неизвестные пары. Принадлежность одной ожидаемой группе задаёт положительные пары; разные группы и случаи задают отрицательные, кроме явных unknownPairs. Поэтому неправильное межслучайное объединение тоже считается FP. Неизвестные отношения исключаются, присоединённые неразмеченные/holdout строки отмечаются unevaluated и не дают TP. Точность/полнота вычисляются по парам, а не общей доле правильных ответов среди всех пар. При нулевом знаменателе JSON содержит null, Markdown — N/A. Рядом с процентами приведены дроби и TP/FP/FN.

Чтобы подтвердить метки, человек проверяет весь случай и заполняет `status: human_verified`, `reviewedBy`, `reviewedAt`. При изменении разметки обновить её version и создать новые отчёты; сравнение с прежним хэшем labels будет помечено несопоставимым. Автоматическое изменение статуса меток не выполняется.

## Артефакты и ошибки

Успешный каталог содержит `result.json`, `diagnostics.json`, `report.md`, `report.json`. Последний записывается после остальных как признак завершения. Ошибки чтения/JSON/валидации сохраняются в `failure.json` и возвращают exit code 1; при ошибке записи могут остаться частичные файлы без успешного report.json. Базовый каталог уже существующего запуска остаётся нетронутым.

RunReport фиксирует хэши входов, labels и конфигурации, commit/dirty, отдельный хэш реализации (src, test, package/lockfile, tsconfig), версии правил/схемы, решения, аудит, provisional eval и время. В ZIP без Git commit/dirty будут null. API calls/tokens/cost равны 0; generation/verifier — null. Время измеряется от входа в CLI, включая Nest bootstrap, до завершения записи результата и диагностики; компиляция, импорт модулей, запись самого отчёта и закрытие контекста не включены. Это локальный wall time, не benchmark CPU или live API.

`compare` проверяет целостность сохранённых решений, сравнивает метрики и изменённые строки. Разные feed/taxonomy/labels/split/schema → несопоставимость и exit code 1, дельты N/A. Версии правил/конфигурации могут изменяться как фактор эксперимента. Нарушение учёта строк и рост FP также возвращают 1. Дельты precision/recall представлены в долях 0–1. Различия времени и метаданных не считаются изменением решений.

Зафиксированные результаты этапа: `reports/B0/`, `reports/B0-repeat/`, `reports/comparisons/before-to-B0/`, `reports/comparisons/B0-repeat/`. Эти каталоги предназначены для хранения в Git; обычные локальные прогоны игнорируются. Краткий итог и передача находятся в `docs/STAGE1_REPORT.md` и журнале `docs/ROADMAP.md`.

Следующий этап — предметные правила B1 по roadmap. React, AI и verifier пока не реализованы. API потребуется на этапе 3, не раньше.
